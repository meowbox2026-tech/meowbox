# MeowBox｜前二十五關難度公式與關卡驗證

版本：2026-09-23

這份文件是給後續關卡設計使用的「可計算規格」。目標不是把每一關壓成同一種難度，而是讓每一關在進入遊戲前能回答四個問題：

1. 這關一定有完整解法嗎？
2. 玩家需要看幾步連鎖與局部重力？
3. 放錯一隻貓時，是溫和的近失敗，還是整關立刻崩潰？
4. 這一關和前一關的難度差，是否在玩家能理解的範圍？

## 先定義 1–25 關的問題

前二十五關使用固定 8×8 棋盤。初始盤面有 `I` 隻固定貓，托盤依固定順序提供 `T` 隻貓；玩家把所有托盤貓放完後才開始消除與局部重力。

令：

```text
A = 棋盤面積 = 8 × 8 = 64
I = 初始固定貓數
T = 托盤貓數
N = 最終總貓數 = I + T
E = 放置開始時的空格數 = A - I
W = 完整解法的消除波數
G = 完整解法中，未被消除的貓向下移動的總格數
K = 托盤中不同配對種類數
```

「把貓放滿」不是難度本身。真正的難度來自：玩家要在 `E` 個空格中，按順序安排 `T` 隻貓，讓最終盤面能依規則清空。也就是一個有順序的配置問題。

## 核心公式

### 1. 盲搜空間：`S`

如果完全不知道解法，按順序嘗試所有空格，配置數量是排列數：

```text
P(E, T) = E! / (E - T)!
S = clamp(log10(P(E, T)) / 30, 0, 1)
```

程式不直接計算巨大階乘，而是逐項累加：

```text
log10(P(E, T)) = Σ log10(E - i), i = 0 ... T - 1
```

這個 `log10` 很重要。若直接用排列數，後期關卡會被幾十位數的結果支配；取對數後，搜尋空間仍然呈現指數成長，但可以和其他因素放在同一個 0–1 尺度。`30` 是目前 8×8、最多 21 隻托盤貓的校準上限；若未來改成更大棋盤，應重新校準，不要沿用。

### 2. 解答緊度：`C`

只看盲搜空間會誤判。某一關可能有很多空格，但只要盤面提示很清楚就不難；另一關可能空格少、答案又非常脆弱，才會真的難。

因此以已知解答為中心做「單格搬移測試」：

1. 先依 `level.solution` 放出一個完整解答。
2. 每次只把一隻托盤貓搬到最終盤面的某個空格。
3. 用真正的 `resolvePlanning` 重播消除與重力。
4. 若仍然 `remaining === 0`，就算是一個附近的替代解。

```text
M = 測試過的單格搬移數
Q = 單格搬移後仍能清空的數量
alternativeRate = Q / M
C = 1 - alternativeRate
```

另外記錄：

```text
forcedPlacementRate = 沒有任何替代位置的托盤貓數 / T
```

`C` 只占總分 10%，因為「只有一個正確位置」不一定等於不好；第一關可以故意有一條清楚的唯一教學線。它更重要的用途是公平性檢查：如果 `forcedPlacementRate >= 85%` 且 `alternativeRate <= 1%`，就標記為 `solution-too-brittle`，要求設計師加視覺錨點、增加撤銷、降低密度或讓這關有更明確的提示。

這是「附近替代解」而不是全域解答總數。全域解答數可能需要指數級搜尋，設計工具可以慢，但遊戲執行期間不能做這件事；因此目前用便宜、可重現的局部測試當第一道門檻。

### 3. 連鎖深度：`H`

每一波消除都會讓一部分貓失去支撐。消除波越多，玩家需要預測的因果鏈越長：

```text
H = clamp((W - 2) / 12, 0, 1)
```

前兩波被視為教學基本成本，不讓第一關因為「至少要消三次」就直接拿到高分。`12` 代表前二十五關中，連鎖波數到約 14 波後已經是高壓段；它不是勝負條件。

### 4. 局部重力負擔：`Gᵣ`

單純把消除組數變多，可能只是多放幾個獨立的三連；真正需要理解局部支撐的是「貓咪被拉下多少格」。

```text
Gᵣ = clamp(G / (2N), 0, 1)
```

`2N` 是目前的校準尺度。這個指標不計算被消除的貓，只計算在每個消除波後仍存活、且位置向下改變的貓。它會把「正確的消除造成正確的連鎖」和「單純盤面變滿」分開。

### 5. 方向與切換：`D`

每個消除群會被判斷為橫、直、斜，或由多條線連成的 `mixed` 群。`mixed` 不是第五種方向，而是提醒設計師這一波同時包含多個幾何關係。

先算：

```text
coverage = clamp((不同基本方向數 - 1) / 2, 0, 1)
switchRate = 方向改變次數 / (W - 1)
M = clamp(0.65 × coverage + 0.35 × switchRate, 0, 1)
```

這樣的權重表示「這關到底教了幾種方向」比「方向切換了幾次」重要。第 2 關可以只教橫線；第 16 關才適合同時出現橫、直、斜與支撐改變。

### 6. 盤面密度：`F`

```text
F = clamp(N / 64, 0, 1)
```

密度會減少可放置的空間，也增加玩家在 8×8 盤面上搜尋視線的負擔。但密度不能獨自決定難度，所以只占 10%。

### 7. 配對種類：`P`

```text
P = clamp((K - 3) / 2, 0, 1)
```

三種貓是基礎辨識；四種是正常進階；五種以上才開始進入明顯的記憶／辨識壓力。這個指標不應該用來掩蓋糟糕的盤面：增加貓種不是修補難度曲線的萬用方法。

### 最終分數

```text
Difficulty = 100 × (
      0.25 × S
    + 0.10 × C
    + 0.20 × H
    + 0.20 × Gᵣ
    + 0.10 × M
    + 0.10 × F
    + 0.05 × P
)
```

程式中的對應名稱是 `searchPressure`、`constraintTightness`、`chainPressure`、`gravityPressure`、`directionPressure`、`densityPressure`、`palettePressure`。所有元件先壓到 0–1，最後才加權，因此設計師能看出是哪一項把關卡推難，而不是只看到一個神秘分數。

以第 1 關為例：`E=58`、`T=3`，所以 `log10(P)=5.3`、`S≈0.177`；完整解法有 `W=3` 波、`G=9` 格下移、`N=9`，使用直線與橫線，三種貓的 `P=0`。代入後得到約 `32.4`，落在第一章的 28–38 區間。這表示它可以有一個很緊的教學答案，但總體仍不應被判成中後期高難度。

## 這個公式如何判斷「正確消除」

難度分析器不自己發明另一套消除規則，而是直接重用遊戲的引擎：

```text
solutionBoard = arrangeCats(level, level.solution)
result = resolvePlanning(solutionBoard)
```

一關只有在以下條件同時成立時才算有效：

- `arrangeCats` 能放入所有解答位置，沒有重複或越界。
- `resolvePlanning` 的 `remaining === 0`。
- 每個消除波的實際方向、清除貓 ID 與局部重力都能從引擎 frame 追溯。
- 起始盤面沒有不需要玩家操作就已成立的連線。這一項由 `planningLevels.test.ts` 持續保護。

因此，「正確的消除」是可重播的引擎事實，不是設計師在表格中手寫的描述；「連鎖」則由 `W` 與 `G` 共同表示。

## 1–25 關的目標區間

分數是校準工具，不是玩家看到的評分。先使用章節區間，讓同章可以有教學關、鏡像關與收尾關，不要求每一關嚴格遞增。

| 關卡 | 角色 | 目標分數 | 設計重點 |
| --- | --- | ---: | --- |
| 1–3 | 基礎教學 | 28–38 | 一次只讓玩家吸收一個新方向，連鎖短而可預測。 |
| 4–10 | 基礎混合 | 35–55 | 引入第四種貓，但不要同時把密度、分支、方向全部拉滿。 |
| 11–15 | 分支與支撐 | 44–62 | 讓玩家開始預測局部掉落；每一關保留清楚的主線。 |
| 16–20 | 多段重力 | 52–78 | 橫、直、斜切換與多段支撐，20 關可以是章節高峰。 |
| 21–25 | 高密度收尾 | 65–82 | 盤面接近滿載，但仍要保留可理解的路線與修正空間。 |

目前額外使用兩條自動警告：

- 相鄰關卡分數變化超過 10：`jump-too-large` 或 `drop-too-large`。
- `forcedPlacementRate >= 85%` 且 `alternativeRate <= 1%`：`solution-too-brittle`。

這不是說被標記的關卡一定要刪掉，而是要求設計師回答「玩家怎麼知道這一格是對的？」。如果答案只有「玩家失敗後重試就會知道」，這通常是不可理解，而不是有趣的難。

### 目前最重要的結論

1. 全部 25 關都有完整解法，程式驗證沒有發現「無法清空」的關卡。
2. 第 1–25 關的分數大致落在預設章節區間內，所以整體方向可保留。
3. 第 6、8、10 關的答案過於脆弱；這三關不是單純「有點難」，而是玩家放錯一格後幾乎沒有附近修正路徑。
4. 第 15、20 關的相鄰跳幅超過 10，應視為需要實測的節點。
5. 第 24、25 關雖然密度與重力很高，但替代解比例反而變寬；它們的難度差異主要來自盤面閱讀，而不是唯一答案。如果第 25 關要有終章感，應增加最後一個可辨識的合流波，而不是只複製第 24 關的壓力。

## 後續關卡的製作流程

### A. 先寫解法，再寫盤面

每一關先決定：

- 玩家第 1 隻貓要完成哪一個可看懂的三連？
- 這一波消除會讓哪一列或哪一欄失去支撐？
- 掉落後下一個三連是橫、直、斜中的哪一種？
- 最後一波要不要是合流、回收或單純收尾？

如果這四件事說不清楚，就還沒有關卡主題；不要先用更多貓把棋盤填滿。

### B. 用固定配方控制一項一項增加的壓力

- 第 1–3 關：一次只加一個方向；`W <= 5`，`G` 保持低，目標分數 28–38。
- 第 4–10 關：加入第四種貓或一次分支，但不要同時增加多段重力；若 `forcedPlacementRate` 超過 85%，至少要有明顯的固定雙貓錨點。
- 第 11–15 關：可以加入兩個同時可消除群，但要用放置順序決定先後；避免「兩個群都看起來一樣，卻只有一個能解」的黑箱。
- 第 16–20 關：主要增加 `G` 與 `W`，不要再靠第五種貓或更小的視覺素材增加難度。
- 第 21–25 關：可以接近 60/64 的最終密度，但 `alternativeRate` 不要因為密度而變成 0；高密度關仍應允許玩家從一次誤判中回到可理解的解法。

### C. 用工具拒絕不合格版本

```bash
npm run analyze:planning
```

看到下面任一項，就不要直接把關卡接進遊戲：

- `authored-solution-does-not-fit` 或 `authored-solution-does-not-clear`。
- `outside-target-band`：與章節定位不符。
- `jump-too-large`：相鄰體感可能斷層。
- `solution-too-brittle`：答案太脆，必須補可讀性或補救機制。

新增關卡時，先把它加入 `PLANNING_LEVELS`，跑分析器，再跑單元測試；不要手動複製上一關的總數並猜測會不會變難。

## 是否要改玩法

目前的「先配置、再播放」玩法可以保留，因為它把玩家的思考階段和消除演出階段分開，所有解法都能由同一個 deterministic engine 驗證。暫時不建議改成隨機補貓或倒數，因為那會把配置難度、反應速度與隨機性混在一起，反而難以知道玩家為什麼失敗。

如果實測證明脆弱關卡讓玩家覺得「完全不知道哪裡錯」，優先順序應該是：

1. 顯示目前貓咪可以完成的主要三連錨點或淡色 ghost，而不是直接顯示完整解答。
2. 脆弱關卡把免費撤銷從 1 次提高到 2 次，僅限 `solution-too-brittle` 關卡。
3. 失敗後保留最後一個仍存活的玩家貓，讓玩家修改造成斷鏈的那一步，而不是整關重來。
4. 只有在玩家已經理解三種方向後，才增加第四種配對種類；不要用新圖案掩蓋支撐規則。

這些都是「降低不可理解性」的改法，不會改變三連、局部支撐與逐波消除的核心身份。

## 研究依據與限制

這個模型不是從單一論文直接抄來，而是把幾個已被使用的概念改寫成 MeowBox 的狀態：

- [Procedural Level Generation with Difficulty Level Estimation for Puzzle Games](https://www.iccs-meeting.org/archive/iccs2021/papers/127460103.pdf)：以 search depth、種類數、額外表面與重複解答等指標，再用加權線性式組合；文中也指出，設計工具可以接受較慢的完整搜尋，遊戲執行端則應保持輕量。
- [Playtesting in Match 3 Game Using Strategic Plays via Reinforcement Learning](https://ieeexplore.ieee.org/document/9034187/)：把可用步數與策略代理完成任務的表現當作關卡 playtest 量測，說明「能不能完成」和「用多少決策完成」要分開看。
- [Search and Match Task: Development of a Taskified Match-3 Puzzle Game](https://games.jmir.org/2019/2/e13620)：以棋盤尺寸、圖案種類、可搜尋目標與連續匹配來控制視覺搜尋負擔；這支持把方向、種類、盤面密度視為獨立因素，而不是只看總格數。
- [Level design complexity in match-three games](https://aaltodoc.aalto.fi/items/40973f30-ade7-4412-98d4-8ea34a0b0d55)：從大量商業三消關卡整理結構複雜度，支持「新機制要分段引入，章節內可有教學回落」的做法。

限制也要明確：目前的分數是結構難度，不是已完成的玩家體感模型。真正上線後，應記錄每關的首次成功率、平均失敗次數、使用提示率、從失敗處修改後的成功率與玩家退出率，再用這些資料調整權重。沒有玩家資料前，不應宣稱 `73` 一定比 `70` 讓所有玩家難三分。
